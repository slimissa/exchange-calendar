## Within QuantOS

The QuantOS ecosystem is a set of registries and consumers that share
one reference-data convention: **one JSON file per standard, four
language wrappers, cross-registry snapshots vendored byte-for-byte,
CI on every push.**

| Consumer | Kind | Version vendored | Fields read | Update trigger |
|----------|------|------------------|-------------|----------------|
| **Tempus** | sibling compiler | `calendar.json`, bundled at build | `sessions`, `confidence`, `as_of`, MICs | schema minor bump |
| **LAS_Shell** | sibling runtime | `calendar.json`, bundled at build | `sessions`, `is_open`, `holidays.explicit`, MICs | schema minor bump |
| **ISO 10383** | sibling registry | none — references EC in its `docs/JOINS.md`; MIC→LEI connector declined (ADR 0011) | MIC cross-check (EC → 10383) | schema major bump or MIC coverage change |
| **ISO 3166** | sibling registry | none — EC vendors *its* snapshot | country cross-check (EC → 3166) | upstream registry release |
| **ISO 4217** | sibling registry | none — no direct edge today | — | — |

"Schema minor bump" means: `schema.json`'s `$id` changes in a way that
adds optional fields. Existing consumers keep working; new fields are
additive. "Schema major bump" means a field was removed or a field's
semantics changed. No consumer has yet crossed a major bump.

## Cross-registry edges

Exchange Calendar **vendors snapshots** of two sibling registries and
**checks them against CI on every push**. This is the same pattern the
ISO siblings use with each other.

| Snapshot | Source registry | File | Regenerated by | Reviewed by |
|----------|-----------------|------|----------------|-------------|
| ISO 3166 country codes | [iso3166](https://github.com/slimissa/iso3166) | `tools/iso3166_snapshot.json` | generator script (see `tools/`) | `tools/check_snapshot_freshness.py` |
| ISO 10383 MICs | [iso10383](https://github.com/slimissa/iso10383) | `tools/iso10383_snapshot.json` | generator script (see `tools/`) | `tools/check_snapshot_freshness.py` |

Both snapshots carry a `review_by` date in their sibling `.meta.json`.
When the date passes, CI warns. Snapshots are refreshed by re-running
the generator against the current `main` of the sibling registry and
committing the result.

**Why snapshots and not live queries:** an exchange's `country_code`
and `mic` fields are validated against a fixed list. If EC queried the
sibling registry at validation time, a sibling release could break EC
CI without any EC change. Vendoring a snapshot decouples the two
release cycles: each repository's `main` is stable, and the coupling
is explicit and dated.

## Distribution shape

Every consumer listed above clones the repository or vendors the JSON
directly.

| Artifact | Available from | Install command |
|----------|----------------|-----------------|
| `calendar.json` | this repo, root | `curl` or clone |
| Python wrapper | `wrappers/python/` | `pip install -e wrappers/python` from a checkout |
| JavaScript wrapper | `wrappers/javascript/` | `npm install ./wrappers/javascript` |
| Rust wrapper | `wrappers/rust/` | `cargo add --path wrappers/rust` |
| Go wrapper | `wrappers/go/` | `go get github.com/slimissa/exchange-calendar/wrappers/go` |
| SQL | repo root, four `exchange_calendar*.sql` files | load the file for your database |
| CSV / TSV | repo root, twenty `exchange_calendar.TABLE*.csv` and `.tsv` files | open the dialect your tool reads |
| Parquet | repo root, five `exchange_calendar.TABLE.parquet` files | read with any Parquet reader |
| CLI | not yet shipped | planned for v3.0.0 |

**SQL exports.** Four files at the repository root load the registry into a relational
database: `exchange_calendar.sql` (ANSI SQL-92), `exchange_calendar.postgresql.sql`,
`exchange_calendar.mysql.sql` (MySQL 8.0.16 or later) and `exchange_calendar.sqlite.sql`
(SQLite 3.37 or later). Each drops and recreates five tables (`exchanges`, `sessions`,
`holidays`, `ad_hoc_closures`, `confidence`) and then inserts every row, so it is not safe
if other tables reference them. Types, keys and CHECKs are specified in ADR 0012. SQLite
enforces foreign keys only when `PRAGMA foreign_keys=ON`, which the SQLite file sets.
Regenerate with `python3 tools/export_sql.py`; `--check` exits non-zero when a committed
file is stale. CI loads the PostgreSQL and MySQL files into real servers (PostgreSQL 15 and
MySQL 8.0) and checks the stored row counts, the stored values and that the keys and CHECKs
are enforced; the SQLite and ANSI files are loaded into SQLite by the test suite.

**CSV and TSV exports.** Each of the five tables (`exchanges`, `sessions`, `holidays`,
`ad_hoc_closures`, `confidence`) is a flat file in four dialects, twenty files at the
repository root. For `holidays`: `exchange_calendar.holidays.csv` (RFC 4180, comma, UTF-8),
`exchange_calendar.holidays.excel.csv` (comma, UTF-8 with a BOM, which Excel needs to read
non-ASCII names correctly), `exchange_calendar.holidays.european.csv` (semicolon) and
`exchange_calendar.holidays.tsv` (tab). The dialects differ only in the delimiter and the BOM.
The header row is the table's column list from ADR 0012 section 5, an absent value is an empty
field, and booleans are `true` or `false`. Sessions and confidence entries are their own files,
never nested into `exchanges`. Regenerate with `python3 tools/export_csv.py`; `--check` exits
non-zero when a committed file is stale.

**Parquet exports.** Each of the five tables (`exchanges`, `sessions`, `holidays`,
`ad_hoc_closures`, `confidence`) is one flat file at the repository root, for example
`exchange_calendar.holidays.parquet`, with the columns of ADR 0012 section 5. Dates use the
Parquet `DATE` type, times are `HH:MM` text, `seq`, `year` and the weekend days are `int16`,
`predicted` and `weekend_exception` are booleans, and an absent value is a real null, not an
empty string. The files are snappy-compressed and each footer records `exchange_calendar.version`
and `exchange_calendar.table`. Reading them needs only a Parquet reader; regenerating them with
`python3 tools/export_parquet.py` needs pyarrow 22.0 or later, and the wrappers do not depend on
it. `--check` compares logical content, not bytes, so a file rewritten with another compression
or row-group size still passes; it exits non-zero when a value, type, row or footer key differs.

**Publication to package registries is deferred.** The wrappers are
not on PyPI, npm, crates.io, or the Go module proxy. The trigger for
publication is a consumer who needs a package-registry install rather
than a repo clone. Until then, cloning the repository is the
supported path.

## Weekend dates and holiday lookups

All four wrappers answer `is_holiday` (`isHoliday`, `IsHoliday`) the same
way: a date that falls on one of the exchange's own `weekend_days` returns
`true` before any holiday data is read, and `is_open` is `false` there.
That has not changed. `weekend_days` is per exchange (Saturday/Sunday for
most, Friday/Saturday for the Gulf exchanges and EGX), so XCAI's Sunday is
a trading day and XETR's Saturday is not.

What changed in v2.15.0 is the holiday *entries*. A holiday that the
generator derives from a recurrence rule is never emitted on a weekend day
of that exchange, because the exchange is closed anyway:

- `list_holidays` and `holiday_count` no longer include a generated entry
  for a weekend date (XETR's Christmas Day on Saturday 2027-12-25 is
  absent). Earlier versions listed 215 such entries.
- A weekend date can still appear as a holiday entry only if it is
  explicit and carries `weekend_exception: true` (XBOM, 2026-11-08).
- Where a rule shifts a holiday, the entry sits on the observed day, not
  the nominal one: on Fri/Sat-weekend exchanges a Friday or Saturday date
  moves to the following Sunday, and XCAI's national days move to Thursday
  (`docs/recurrence_rules.md`).

If you read holiday names from `list_holidays` to label weekend dates,
look the name up from the nominal date yourself; the registry no longer
lists it. If you only ask whether the exchange is open, nothing changes.
The rule is pinned by the cross-language fixture queries
`is_holiday_weekend_no_entry`, `holiday_entry_weekend_none`,
`is_holiday_weekend_exception`, `is_holiday_xcai_sunday_trades` and
`is_holiday_xcai_thursday_observed`.

## Update protocol

When the registry ships a new version, the effect on a consumer
depends on the change class. The three classes follow semantic
versioning of the registry's schema:

### Patch release (`2.1.0` → `2.1.1`)

Data corrections, new fetchers, or tooling changes. No field added or
removed. Consumers do **not** need to update. The schema `$id` is
unchanged.

### Minor release (`2.1.1` → `2.2.0`)

New optional fields. Consumers that read the new fields must update
their vendored `calendar.json`. Consumers that don't are unaffected —
the schema is a superset of what they read. The `$id` changes.

Re-vendor with:

```bash
git fetch origin
git checkout origin/main -- calendar.json
# Then re-run whatever generates the vendored copy inside the consumer.
```
## Major release (2.2.0 → 3.0.0)

A field was removed, renamed, or had its type changed. Consumers must
update their code, not just their vendored file. This class of change
has not yet occurred; the current trajectory (additive fields only)
keeps it unlikely for the foreseeable future.

The historical layer — planned as v4.0.0 — will be the first
candidate for a major bump, because it will change as_of from a
projection over current state to a real historical snapshot. That
change will be announced here.

Open a PR that adds one row to the
external adopters section with:

    The version you vendor (tag or commit SHA).

separate PR against wrappers/.
